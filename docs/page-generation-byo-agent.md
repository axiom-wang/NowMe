# NOWMe 页面生成方案：本地 Agent 与网页内自带 API 两条路线

本文说明每位成员的个性页面是怎么做出来的：谁收集信息、谁生成、不同圈子的页面有什么不同、怎样保证效果精彩，平台不提供模型 Key、不承担模型调用费用，也不让共享的墙失控。

标记约定同 MVP 文档：

- **[已决定]**：本版定下的方案，变更需要重新讨论。
- **[假设]**：方案依赖、尚未验证的判断。
- **[待定]**：需要原型或测试后才能确定。

## 1. 目标与约束

| 目标 | 说明 |
| --- | --- |
| 让人眼前一亮 | 页面不是填空式模板，可以有动效、Canvas、交互和独特版式 |
| 平台模型费用可控 | 两条路线平台均不承担模型费用；网页内创作由用户自带 API，服务商直接向用户计费 |
| 贴合圈子 | 同一个人在不同圈子里的页面侧重不同，例如黑客松突出能力，兴趣社群突出爱好 |
| 墙整体协调 | 每页的内容可以自由发挥，但放到墙上要像一面展览墙，而不是一团混乱 |
| 安全 | 用户上传的页面带有代码，不能危害平台和其他成员 |
| 不编造 | 页面只能使用主人提供并确认过的信息（MVP 文档第 6 节） |

前提 [假设]：首批目标用户大多数已经在用自己的编程 Agent（Claude Code、Codex、Cursor 等），愿意在 Agent 里执行一条指令来生成页面。

## 2. 总体方案 [已决定]

两条路线共用同一个 NOWMe Skill、同一份输出契约、同一套校验和展示，区别在于 Agent 在哪里运行、用户如何提供模型访问能力。

| | 本地路线（免费，默认） | 网页内自带 API 创作（平台免费） |
| --- | --- | --- |
| 适合谁 | 有自己 Agent 的用户 | 有模型 API、希望直接在网页创作的用户 |
| ① 收集信息 | 用户的 Agent 采访，结合本地画像 | 平台在应用内用 AI 采访 |
| ② 生成页面 | 用户的 Agent + NOWMe Skill | 平台在服务器上运行同一个 Skill |
| ③ 修改 | 在本地对 Agent 提修改 | 在应用内用日常语言提修改 |
| 提交与发布 | `nowme submit` 上传，在应用内确认并发布 | 生成结果直接存为版本，在应用内确认并发布 |
| 平台的模型费用 | 0 | 0；模型服务商向用户自己的 API 账号收取费用（第 9 节） |

平台在两条路线中都负责：墙与邀请、墙的情境、校验与审核、托管、缩略卡确认与发布、浏览墙与"想聊这个"。

本地路线的流程：

```
应用内                          用户的 Agent（本地）                     平台
────────                       ─────────────────────                  ──────
加入墙
显示指令：
/nowme-page <wall-id> <token> ──▶ nowme fetch：用 token 换取页面凭证 ──▶ 核销 token，签发凭证
                                  拉取墙的情境（场景类型、组织者的话）
                                  读取本地画像，按场景指南采访补全
                                  整理 brief，给用户过目确认
                                  按 Skill 规范生成页面
                                  本地校验 + 截图自查
                                  用户在本地预览、提修改
                                  nowme submit（带页面凭证）──────────▶ 重新校验、审核
                                                                        生成字体子集，存为一个版本
应用内预览 ◀───────────────────────────────────────────────────────────┘
确认缩略卡与公开内容 → 发布到墙
```

## 3. 场景指南的生成部分 [已决定]

每种场景类型配一份场景指南，同时用于收集信息和生成页面。收集信息的部分（采访内容、生成前必须有的信息、接话点类型、默认边界、页面目标）见[信息收集与 brief](brief-collection.md)第 4 节；这里只列生成时用到的部分。

| | 黑客松 / 创业营 | 兴趣社群 [假设] | 社团招新、新成员入群 [假设] |
| --- | --- | --- | --- |
| 建议区块 | 项目展示、能力标签、组队需求 | 收藏、作品墙、入坑指南 | 自我介绍、想尝试的事、"可以来问我" |
| 视觉基调（只是建议） | 偏利落、科技感 | 跟着兴趣本身的气质走 | 偏活泼、个人化 |

规则：

- 生成时按墙的情境从画像中**挑出一部分、换一种讲法**，而不是把同一份内容换个皮肤。主人说明了本页意图时，以主人为准。
- 缩略卡结构在所有场景下保持一致（名字、一行介绍、2–3 个接话点），只是接话点的类型随场景变化，保证墙的协调。
- 页面沙箱禁止联网，可运行的 demo 只能以截图、录屏动图或 `nowme.openLink()` 外链的形式出现，场景指南要写明这一点。

## 4. 第一步：收集信息，形成 brief

见[信息收集与 brief](brief-collection.md)：原则、采访流程、场景指南、主人主动提供的内容、本地路线的隐私规则和 brief 结构。本地路线由用户的 Agent 采访，平台托管路线由平台在应用内采访，两者产出同样结构的 brief。

## 5. 第二步：用 Skill 生成页面

### 5.1 Skill 的组成

| 组成 | 作用 |
| --- | --- |
| `SKILL.md` | 采访与生成流程、输出契约、设计原则、隐私规则、禁止事项 |
| 场景指南 | 每种场景的侧重、采访重点、建议区块、接话点类型、视觉基调 |
| NOWMe Kit | 平台托管的基础 CSS 变量、字体清单（见 5.4 节）、若干现成动效和组件；拉高弱模型的质量下限 |
| 示例页 | 每种场景 1–2 个风格差异大、质量高的示例，附上设计思路 |
| `nowme` 命令行工具 | `fetch`（换取页面凭证并拉取墙的情境）、`validate`（校验）、`preview`（预览和截图；随 Skill 分发的版本由服务端渲染）、`submit`（上传素材与页面）；凭证规则见 6.1 节；随 Skill 包一起分发（`scripts/nowme.mjs`） |

Skill 格式优先兼容 `SKILL.md` 规范；不支持的 Agent 提供等价的纯文本指令。各家 Agent 的兼容情况 [待定]，需要实测。

**分发与安装 [已决定，T3.6，详见 contracts 4.5]**：真实用户手里没有本仓库。源码在主项目维护，完整成品自动同步到公开仓库 [axiom-wang/nowme-skill](https://github.com/axiom-wang/nowme-skill)，GitHub Releases 提供带 sha256 的归档；主站 `/skill` 保留安装指引和本地镜像，Skill 包里自带打包好的单文件 `nowme` 命令行（`scripts/nowme.mjs`，只需要 Node 22），所以“装好 Skill”也会取得对应版本的命令行。命令行在本机没有浏览器，`preview` 由服务端用同一套沙箱渲染截图后返回（不保存）。

- 安装说明是**通用的**：不写具体 Agent 的名字和目录；推荐用户把一句话（“请按 https://raw.githubusercontent.com/axiom-wang/nowme-skill/main/install.md 安装 NOWMe Skill”）发给自己的 Agent，由 Agent 判断装到哪里，不确定就问用户。
- 装好后需要**重开会话**；用户让 Agent 运行 `scripts/nowme.mjs --version` 自检；连接后工作区显示 Skill 版本，过旧时提示更新。
- 工作区始终显示安装说明，并解释 `Unknown command` 的原因（当前会话没有加载 Skill）与解决办法；不支持 Skill 的 Agent 用纯文本说明，它的第 0 步同样指向这个工具包。
- 可以额外配置一个 Skill 市场渠道（例如 SkillHub、skills.sh 的安装命令），配置了才显示；默认使用公开 GitHub 分发源，安装不依赖本机主站。

### 5.2 输出契约 [已决定]

```
page/
├── index.html      # 自包含的单文件页面，HTML/CSS/JS 都内联
├── assets/         # 页面用到的图片，提交时上传到平台
├── card.json       # 缩略卡：名字或昵称、一行介绍、2–3 个接话点
├── cover.png       # 墙上的静态封面，可由 preview 自动截图
└── manifest.json   # 版本、场景类型、使用的 Kit 版本、动效强度、用到的字体、额外字符
```

页面必须满足：

- **移动端优先**：以 375px 宽为基准，在微信内置浏览器里正常显示。
- **可以自由创作**：CSS 动画、Canvas、WebGL、SVG、交互脚本都允许。
- **不能联网**：不使用 `fetch`、XHR、WebSocket，不加载外部资源；只引用 Kit 和 `assets/` 中的文件，提交后由平台改写为素材域名下的地址。
- **字体只从 Kit 中按名称选用**：不内联字体文件或 base64 字体，也不把字体放进 `assets/`（5.4 节）。
- **不能存储和跳转**：不使用 cookie、localStorage，不跳转顶层页面，不使用表单提交。外部链接通过 Kit 提供的 `nowme.openLink()` 交给平台处理。
- **只使用 brief 中的信息和主人主动提供的内容**（[信息收集与 brief](brief-collection.md)第 5 节）：不编造经历、数字或引语。
- **主要区块有稳定标识**（`data-nm-id`），方便之后按区块修改。
- **支持 `prefers-reduced-motion`**，体积有上限（暂定 `index.html` 不超过 300KB，不含图片和字体；字体单独计算，见 5.4 节）[待定]。

### 5.3 生成流程（写在 Skill 里）

1. 读取 brief 和场景指南，先写一段设计构想：这页想给人什么感觉、核心视觉、区块安排。
2. 从 Kit 和示例中选一个起点，或者完全自由创作。
3. 生成 `page/`。
4. 运行 `nowme validate`，有问题就修复。
5. 运行 `nowme preview` 截图，按 Skill 中的自查清单审视效果（层次、留白、文字可读性、是否"像这个人"、是否符合这面墙的场景、是否有 AI 模板感），修改后再截图，至少一轮。
6. 把预览交给主人，进入第三步。

### 5.4 中文字体 [已决定]

一款完整的中文字体有数 MB，无法放进页面，也不能让手机每次打开都下载。做法是**页面只按名称选用字体，平台在提交时按页面实际用到的字生成子集**。

- **Kit 提供字体清单**：少量中文和西文字体，均为允许子集化和网页分发的开源授权（例如 SIL OFL）。页面通过 Kit 的 CSS 变量或字体名称引用，清单之外的字体不能使用；想要新字体，由平台评估后加入清单。
- **平台生成子集**：每次提交时，平台收集页面用到的字，包括 `index.html` 中的文字、无头浏览器渲染后的文字和 `manifest.json` 中声明的额外字符，为每款字体生成只含这些字的 WOFF2 文件，放在素材域名下，并改写页面中的字体引用。子集文件属于这一版本，之后 Kit 更新字体也不影响已发布的页面。
- **脚本动态生成的文字**：打字机效果、随机切换的句子等，在首屏渲染时不一定出现。`nowme validate` 扫描脚本中的中文字符串，自动补进 `manifest.json` 的额外字符；仍未覆盖的字会回退到系统字体，validate 给出警告。
- **本地预览与提交后一致**：`nowme preview` 在本地执行同样的子集化，主人在本地看到的就是提交后的效果。
- **字体预算** [待定]：每页最多使用 2 款中文字体（每个字重计为 1 款）；子集后的字体总大小设上限，具体数值由真机首屏耗时测试确定。页面文字通常只有几百到一两千个不同的字，子集后每款预计在几十到几百 KB [假设]。

## 6. 第三步：修改与提交

- **修改**：本地路线中，主人直接对 Agent 说"第二块换成拼贴风格"，Agent 按 `data-nm-id` 只改目标区块，费用由用户自己承担。平台托管路线中，主人在应用内提出修改，修改使用用户配置的 API，由服务商计费（第 9 节）。
- **提交**：本地路线用 `nowme submit` 上传 `page/`，以页面凭证（6.1 节）认证，可以多次提交；平台每次提交都存为一个版本（对应 MVP 文档的 W10）；校验不通过时返回具体原因，由 Agent 修复后重新提交。平台托管路线的生成结果直接存为版本。
- **发布在应用内完成**：主人在应用里预览，确认缩略卡上的一行介绍和接话点（W11），确认公开内容与联系方式，然后发布（W12）。Agent 不能绕过这一步直接让页面上墙。
- 恢复旧版本、撤下和删除都在应用内完成，与 MVP 文档一致。

### 6.1 本地路线的凭证 [已决定]

本地路线需要多次提交，所以用两种凭证：指令中的一次性 token 只用来开始，之后的拉取、提交和事件上报都用页面凭证。

| | 一次性 token | 页面凭证 |
| --- | --- | --- |
| 从哪里来 | 应用内的 Agent 指令 | 首次 `nowme fetch` 时用 token 换取 |
| 作用范围 | 这一位成员的这一个页面 | 同左 |
| 能做什么 | 换取页面凭证 | 拉取墙的情境、提交版本、上报 W20 事件 |
| 何时失效 | 换取成功后立即失效；未使用时按有效期过期（[信息收集与 brief](brief-collection.md)第 6 节） | 主人在应用内断开本地 Agent、退出墙或删除页面时失效 |
| 保存在哪里 | 指令文本中 | 本地 `~/.nowme/credentials`，只有本人账户可读；不写进 `page/`，不随提交上传 |

- **页面凭证不能发布**：发布、恢复版本、撤下和修改公开范围都只能在应用内由主人登录后完成。凭证泄露时，持有者最多只能提交新版本，无法让内容上墙。
- **应用内可见、可断开**：创作工作区显示本地 Agent 的连接状态、最近一次提交时间，每个版本标明来源；主人可以随时断开，旧凭证立即失效。
- **换电脑或重新连接**：在应用内重新生成指令，用新 token 换取新凭证，旧凭证同时失效。
- 平台托管路线在应用内完成全部操作，不需要页面凭证。

## 7. 平台托管路线

- **同一个 Skill**：平台服务器使用当前用户账号中加密保存的 API Key 运行同一个 Skill，包括采访、生成、校验和截图自查。不另做第二套生成系统。
- **采访在应用内进行**：按[信息收集与 brief](brief-collection.md)的流程和场景指南，以选项、标签和图片上传为主，配合 AI 追问；长期画像和 brief 保存在平台，按 MVP 文档第 6 节管理，组织者看不到。
- **模型选择**：采访用便宜、够用的模型；生成用效果更好的模型。固定的 system prompt 和 Skill 内容开启 prompt caching。用户可为采访和生成分别选择服务与模型，也可共用服务与 Key。
- **执行隔离**：生成和截图在隔离环境中运行，每次任务结束后清理。
- **失败处理**：模型服务商可能仍收取费用。失败保留素材、brief 和已有版本，显示检查配置或重试的指引。

## 8. 质量：三层保障

Skill 对模型来说只是"建议"，模型越弱越容易偏离，所以质量和安全不能只靠 Skill。

| 层 | 在哪里运行 | 负责什么 |
| --- | --- | --- |
| Skill 规范、场景指南、Kit 与示例 | Agent（本地或平台） | 决定质量下限：弱模型用 Kit 拼出来也不难看，强模型可以超越 Kit |
| 校验和截图自查 | Agent（本地或平台） | 尽早发现违规；用"截图、审视、修改"的循环提升效果 |
| 平台重新校验和沙箱 | 平台 | 真正的安全边界，不信任客户端的校验结果 |

模型之间的差异只影响页面有多精彩，不影响安全和墙的稳定。

## 9. 免费平台与用户自带 API [已决定，2026-11-07]

原按墙收费、个人付费、购买次数和少量免费额度方案全部取消，不保留后续收费阶段。

- 平台免费提供墙、采访界面、生成编排、校验、预览、版本和页面托管，不提供公共模型 Key、不补贴或代付模型费用。
- 用户先在账号的 **AI 设置**（`/account/ai`）填写服务商、Base URL、API Key 与模型，采访和生成可分别配置，也可共用服务与 Key。
- 所有模型请求由服务器使用当前用户的 Key 发出；服务商直接向用户计费。平台不转售 API、不充值、不扣次数，失败请求也可能计费。
- Key 使用 AES-256-GCM 加密保存在账号下，只有服务端环境持有主密钥；跨设备登录可用，界面不回显完整 Key，支持更换和删除。更换服务地址时必须重新填写 Key。
- 账号未配置时入口仍可见并引导配置；凭证失效时提示检查，不使用平台 Key 兜底。删除后停止后续模型请求，已发出的请求可能继续完成或计费；素材、brief 与页面保留。
- 默认每页滚动 24 小时最多 10 次生成/修改任务、20 次采访调用，每页同时 1 个任务；这些是可配置的运行保护限制，与付费无关。单次任务最多 30 轮工具调用、10 分钟。
- 自定义模型服务须为公网 HTTPS；逐次请求检查 DNS 并固定实际连接地址，禁止重定向。仅显式开发配置允许服务器本机回环服务；地址不代表访问者电脑。

## 10. 安全与托管 [已决定]

- **独立域名**：用户页面放在与主站不同的域名下（例如 `*.nowme-pages.example`），即使脚本出问题，也拿不到主站的登录状态。
- **沙箱 iframe**：`<iframe sandbox="allow-scripts">`，不给 `allow-same-origin`、`allow-top-navigation`、`allow-forms`。
- **严格 CSP**：`default-src 'none'`；只放行内联脚本和样式、Kit 域名、素材域名；`connect-src 'none'`。
- **素材经过平台**：图片随提交上传，由平台改写成素材域名下的地址。
- **服务端校验**：重复本地校验的全部规则；用无头浏览器渲染页面，检查脚本报错和首屏耗时，提取渲染后的文字和截图用于内容审核，并据此生成字体子集（5.4 节）。
- **内容审核**：文字和图片在发布前送审，具体要求按所选平台核验（MVP 文档第 14 节）。

## 11. 墙上的展示
